# Post-connection bidirectional session fix — 2026-10-16

The actual public 0.4.1 build was reproduced with two independent browser contexts. Both real DataChannels reached open before the test asserted file controls; the assertion failed because Send Files was absent. Instrumentation observed RTCPeerConnection/ICE state, channel readiness, WebSocket readyState, selected files and rendered status without recording capabilities or ICE addresses. The supplied screenshot shows the same normal-screen failure. This is a confirmed rendering/state bug, independent of an unverified NAT/TURN problem.

Root causes: the sender dropzone was hidden whenever `sharing && (!completed || busy)`, so it disappeared precisely when a live session needed it. The joining device was excluded by `mode !== Receive Files`. A status string containing `approval` took priority over connected state, conflating room approval with per-file acceptance. The previous public reverse-transfer regression used Advanced controls, leaving this consumer UI gap untested; those results did not prove normal post-connection bidirectionality.

The fix makes room creation/joining roles independent of post-connection transfer permissions. Both paired devices see Send Files and Share Text, sending is gated on real channel readiness and a non-conflicting transfer, selections remain staged, and an explicit Send starts receiver-approved offers. Transfer acceptance is labeled separately from pairing. Typed connection phases track room, approval, negotiation, channel-ready, disconnection, failure and expiry. Diagnostic DOM attributes expose safe phase/member/channel state for regression evidence, without displaying technical details in the consumer UI. Text remains escaped React text, with copy/history controls.

Validation before deployment: lint, TypeScript/build and 14 frontend unit tests passed. Production-built online suite: 9 passed, including real A→B (1,048,583 bytes) and B→A (7 binary bytes) saved-byte equality, both-direction text, mobile actions, and no unexpected page errors. Actual Vite development server plus a separate signaling process: the new bidirectional scenario passed. Existing desktop suite: 8 passed. Backend compatibility: 78 passed, 7 unconfigured provider cases skipped. Windows executable/ZIP not rebuilt; ZIP SHA-256 remains CF8E76E3D14FA88FA3D77F2629BBFCE155E58A1C38F7BA05B7DBB1EBF5590E18.

Existing Pages/Render projects and manual-only authorization are reused. Public deployment and fresh public transfer verification are recorded below. Physical cross-network PC/phone file transfer is not yet verified. The user reports devices can pair, but that does not establish successful file transport. TURN remains absent, and restrictive NAT/firewalls remain a separate limitation. Earlier production deployment remains available for rollback.

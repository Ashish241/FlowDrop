# Optical transfer reliability — 2026-10-17

## Reported failure and what the evidence establishes

The user physically observed a roughly 64 KB file producing 328 QR frames and remaining incomplete after two animation cycles. The original file, camera captures and receiver counters were not supplied. We therefore cannot identify which physical frames were missed, or claim an exact camera/exposure cause.

The old implementation has an exact reproducible explanation for the count: a 65,536-byte fixture becomes `ceil(65536 / 200) = 328` data frames. Its JSON/Base64url format repeats transfer ID, SHA-256, filename, size and MIME metadata on every QR. The benchmark fixture’s first frame contains 477 characters for 200 file bytes, uses QR version 17 at M correction, and has about 210 metadata characters plus 267 Base64url characters. The receiver requires all original chunks. Repetition is not erasure correction: a phase-locked sampling test sees the same 164 even-numbered frames on both cycles and still lacks 164 chunks. Complete, out-of-order legacy input does reconstruct correctly, so the tests do not establish a binary concatenation/off-by-one defect.

Confirmed acquisition/recovery weaknesses: no selective retransmission or file-level FEC; jsQR runs synchronously on the UI thread; no decode-attempt/invalid-frame counters; and a fixed interval advances the sender independently of image loading, with unguarded asynchronous QR generation. None of these observations proves that a particular phone had an exposure or focus fault. The practical fix addresses frame loss, recovery and scheduling rather than simply speeding animation up.

## Protocol and bounds

The new v3 protocol uses `FD3:` plus QR-alphanumeric Base45 over a compact binary envelope. It avoids JSON/Base64 data expansion in the new sender. Each frame repeats sufficient metadata to survive a missing first or last frame: version/flags, 128-bit random transfer ID, original and encoded sizes, chunk size/count, parity configuration, frame index and payload length, UTF-8 filename/MIME lengths, original SHA-256, and a CRC-32 covering the full frame. All integer fields use network byte order. SHA-256 gates completion and downloads; CRC rejects damaged frames before erasure reconstruction. Neither authenticates a sender.

Chunks are configurable at 200/400/600/800 bytes. Files remain bounded at 64 KiB; text at 16 KiB. Header/name/MIME/payload lengths, indices, transfer consistency and total sizes are checked before storing data. Duplicate frames do not replace valid chunks; conflicting/mixed transfers produce errors and preserve existing data. Gzip is used only when it saves at least 64 bytes, with bounded streamed decompression and original-size/hash verification. Empty files and Unicode names are supported. The updated receiver still accepts legacy v1 text and v2 file frames; v3 sending/recovery needs the updated receiver, so reload both devices. Existing Windows binaries retain their previous implementation.

FEC uses the pinned MIT browser-compatible `@digitaldefiance/reed-solomon-erasure.wasm` 1.0.2, a 2026 browser-maintenance fork of the archived Subspace wrapper. Package and upstream references: [fork](https://github.com/Digital-Defiance/reed-solomon-erasure.wasm), [archived predecessor](https://github.com/autonomys/reed-solomon-erasure.wasm), [QR encoder documentation](https://github.com/soldair/node-qrcode). The dependency was installed from npm, its API/license inspected, npm audit reported zero vulnerabilities, and its MIT notice is shipped as `optical-codec-LICENSE.txt`. This is not a claim of an independent security audit. The WASM bytes are bundled inline: no CDN/runtime FEC fetch is needed after loading.

Data is grouped into up to eight shards, with configurable 0/1/2/4 parity shards. With two parity shards, any two missing shards in a group can be reconstructed if the other required group shards arrive. Three or more erasures in that group may require selective recovery. A single-data-frame transfer uses no extra parity and remains a single QR. Playback interleaves data blocks to spread short consecutive losses. The receiver records available data chunks, missing IDs, duplicate/invalid/mixed frames, FEC reconstruction count and retained payload bytes. Recovered counts describe reconstructions at the time of receipt; some original copies may arrive later.

## Recovery and camera behavior

`FDR3:` recovery requests contain transfer ID, original data-frame count, page/total page count, bounded missing IDs, CRC and measured camera decode rate. At most 128 missing IDs per QR, up to three pages, cover the maximum 328 data frames. The sender must scan every page of the matching transfer before sending only the requested data frames. Missing lists also support manual one-based input such as `1,4-8,27`. Existing chunks are merged, never cleared for recovery or Stop/Start camera. Reset explicitly starts another receiver session. All this works without a communication network.

The sender renders only the current QR, with stale-generation guards. Animation is scheduled after image load; actual image-load intervals are displayed. Pause/resume, repeat, manual frame stepping, QR size and fullscreen controls are available. Black/white rendering uses a four-module quiet zone and M QR correction. Presets are Slow 1400 ms, Normal/initial Auto 1000 ms, Fast 600 ms. Estimates are one-cycle estimates, not delivery guarantees. Fullscreen respects viewport bounds and unsupported browsers receive enlargement guidance.

Decoding runs in a same-origin Web Worker with a single capture in flight and bounded resolution. A decoder attempt can try up to three scales to mitigate sampling aliasing; diagnostics measure total elapsed decoder time. Camera requests offer 720/1280-pixel profiles, environmental-facing preference and focus/framing guidance. No QR, decoder errors and invalid protocol frames are distinguished. Imported images and camera input are separately identified; imported-image throughput is not passed off as physical-camera feedback. Auto adjusts dwell only after explicit receiver recovery feedback; it does not claim a two-way optical link or silently change chunk geometry mid-transfer.

## Measured capacity and performance

Exact observations are in `OPTICAL_BENCHMARK.json`, `OPTICAL_SAMPLING.json`, `OPTICAL_FEC.json` and `OPTICAL_RENDER_TIMING.json`. They use deterministic 65,536-byte binary fixtures and actual QR raster decoding on this PC, not a phone camera.

| Payload bytes | Data + parity (2/group) | Total QR frames | First QR version/M | First QR characters |
|---|---|---|---|---|
| Legacy 200 JSON/Base64url | 328 + 0 | 328 | 17 | 477 |
| v3 200 | 328 + 82 | 410 | 13 | 477 |
| v3 400 | 164 + 42 | 206 | 18 | 777 |
| v3 600 | 110 + 28 | 138 | 22 | 1077 |
| v3 800 | 82 + 22 | 104 | 25 | 1377 |

The fixture’s binary header is 115 bytes, including filename/MIME and CRC. A full 400-byte data frame is 515 binary bytes before Base45 (77.7% original-data efficiency before parity), then 777 QR-alphanumeric characters. Character counts are not equivalent QR capacities: alphanumeric encoding packs more tightly than byte-mode JSON. Gzip may substantially reduce compressible files, but random input is not compressed.

The recorded normal raster profiles at 600 and 360 pixels decode all four sampled 400-byte frames. The deliberately degraded 240-pixel/blurred profile does not decode them all. Larger candidates show different failures at particular scales; one 800-byte profile improves from 1/4 to 4/4 with bounded scale fallback, while other degraded cases still fail. Four samples/profile are limited synthetic evidence, not a statistically validated device model. The conservative default remains 400 bytes; 600/800 are options for a calibrated receiving camera, not an automatic largest-payload choice or a claim of physical optimality.

At 1000 ms, the 206-frame default cycle estimates 206 seconds, versus about 197 seconds for the old 328-frame/600 ms cycle. It is **not** advertised as faster simply because its frame count fell by 37.2%. The reliability benefit is parity, explicit missing-frame repair and avoiding complete restarts. End-to-end time on real phones still needs measurement. Actual browser image-load timing at the configured 1000 ms is recorded separately from camera FPS.

The phase-sampling harness decodes 246 actual QR rasters: two repeated scans retain 82/164 data chunks, the recovery QR requests the missing 82, and selective raster retransmission produces the exact original hash `fd3623ef92dc587838fcebecdfd88e5288178c52a0b905294d8d0ee9ef0d2634`. The browser E2E selects the same 64 KiB fixture, imports actual sender-generated QR images with deliberate omissions and a duplicate, exchanges an actual reverse recovery QR, and compares the downloaded bytes with the original while both browser contexts have networking disabled. This is stronger than protocol-only input but remains simulated optical acquisition.

Resource checks bound decoded data/parity storage below 200 KB in the many-frame protocol tests, use one decoder image in flight, and avoid holding hundreds of QR bitmap URLs. A capture bitmap is at most 1280 pixels on its long side; fallback pixel buffers and browser decoder/WASM overhead are additional memory. This is not a whole-browser peak-heap certification. The Online production bundle is approximately 680 KB minified (268 KB gzip), with a roughly 131 KB decoder worker; the Vite large-chunk warning remains visible and is not a build failure.

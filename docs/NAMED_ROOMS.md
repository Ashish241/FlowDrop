# Named rooms and selected-recipient sharing — 2026-10-16

## Scope and architecture

The earlier Online dashboard mapped a single creator/receiver pair to room membership and transport state. It could not honestly support named rooms or one-to-many transfer by changing labels. The new Online-only dashboard uses `/signal/v2` with server-authoritative members and a bounded addressed WebRTC mesh (maximum 8 members). Stable random member IDs and individual hashed capability tokens are distinct from display names. Deterministic member-ID ordering elects the offerer per pair, avoiding simultaneous-offer collisions. Each pair reuses the existing OnlinePanel streaming, acknowledgement, pause/cancel and SHA-256 engine. File bytes and text use encrypted DataChannels; signaling forwards only allowlisted addressed negotiation metadata.

Legacy v1 signaling and desktop OnlinePanel remain available for existing clients. Offline LAN host-mediated transfers and Optical Share were not replaced. Windows executable/ZIP artifacts are not rebuilt. The former consumer approval UI tests are retained as historical source; their UI-specific expectations are superseded by `rooms.spec.ts`. Existing v1 protocol/combined tests remain relevant regression coverage.

## User experience

Create Room / Join Room require a trimmed 1–32 character device name. Names are React text, never HTML or credentials. Optional browser-local name storage is an explicit checkbox. Invitation fragments contain only a temporary six-digit code; no owner capability. Members join immediately with their own token, while incoming file acceptance remains mandatory. Invitations provide QR, Copy Code and Copy Link. Creators can lock new joins and end the room; participants can leave. Duplicate names are allowed, while recipient selection and authorization always use stable IDs.

The room dashboard lists members and actual pair transport states, retains visible file/text actions while connecting, supports select-all/clear/count and snapshots selected eligible IDs when sending. New arrivals are never added to an active send. Each recipient has its own transfer engine and acceptance/decline, pause/cancel, progress, speed, ETA and integrity result. One declined or slow recipient cannot stall another recipient's pair. Up to seven independent recipient engines run concurrently; each sends files sequentially with the existing bounded buffers/credit window. Batches are capped at 128 files, show a manifest, and can be explicitly accepted as a batch. Subsequent files are accepted only when their name/size/type match the authorized manifest sequence. Successful history is session-scoped and bounded to ten entries per peer.

Authenticated rename events change only the current member. Every socket receives the authoritative updated list. Rename does not replace the pair or channel, so pending/ongoing transfers continue. Other members cannot be renamed by supplying an ID. Device-type icons are cosmetic client hints.

Signaling reconnects use bounded backoff. Pair connections are renegotiated after signaling loss, and selected File references stay in the dashboard. Interrupted files require retry from the beginning; byte-offset resumption across a lost WebRTC connection is not claimed. Refresh recovers the room capability from sessionStorage, not localStorage or URL; browser security requires file reselection after a full refresh. Ending/leaving clears the room state and history. Server restarts invalidate temporary rooms. Open-room expiry is one hour; invitation expiry is ten minutes. Locked rooms reject new members but existing members may reconnect.

## Security and operation

Exact origin CORS/WebSocket checks remain enabled. Code attempts have per-IP 20/minute temporary lockouts; ICE/leave use separate 60/minute budgets. Trusted-proxy parsing uses the existing explicitly configured helper and never blindly trusts forwarding headers. Room and member capacity, WebSocket message size, event frequency and authentication timeout are bounded. Tokens are hashed on the server, sent in the initial authenticated WebSocket frame and HTTP Authorization headers, and excluded from roster broadcasts/URLs. Addressed signaling overwrites the sender ID and refuses unknown/self recipients. Binary/file payloads are not forwarded through signaling.

V2 is intentionally a single-instance in-memory protocol for the existing Render Free service (`--workers 1`). It is not attached to the legacy REDIS_URL distributed branch and must not be advertised as a cross-worker room protocol. Scaling v2 requires a shared-authority implementation before enabling more workers. No paid infrastructure is introduced.

### Completion-state safeguard

A final actual DataChannel negative test sent `verified` before file acceptance, then sent an ordered text marker to prove the event had been processed. The pre-guard public frontend incorrectly displayed Delivered; this was reproduced as an expected failing regression. The transfer engine now requires an active send, a pending verification callback, and acknowledgement of the complete file before accepting a `verified` event. The new regression and all five local room acceptance scenarios pass with this guard. This prevents an early peer control message from falsely marking transport completion; it does not claim cryptographic proof of a dishonest recipient's own actions. Frontend deployment metadata records `integrityGuard: true` for verification.
